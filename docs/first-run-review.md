# First-time setup and session roles

**v0.5 experimental prerelease.** Use the [shared skill](../skills/harness-interop/SKILL.md) and [onboarding guide](onboarding.md). Respect current native execution restrictions and record actual failures; do not infer a universal restriction from an earlier deployment batch.

1. Ask the user for the private state folder before writing anything. Record the chosen working folder for throwaway nudges separately; the target retains its own registered cwd. Use existing compatible Node, local MCP stdio and shared SQLite. Docker builds source bundles; the optional HTTP path is v0.4 compatibility only.
2. Record actual harness/engine versions, host/server and exact native binding, selectable models/access evidence, effective privileges and supported retention choice. Unknown capabilities remain unknown. No inference is needed to inspect interfaces.
3. An authorized operator issues an exact endpoint/peer enrolment. The receiving session registers with separate private session/wake credentials. Native snippets are emitted for explicit setup, never auto-written.
4. Discover permitted endpoints with attributed observation age. No catalogue or allowance snapshot authorizes model switching, spending or dispatch. Plain prompts stay local.
5. Configure/validate trusted notifications and explicitly requested worker adapters separately. Check the runtime/connection owner; do not assume one stdio process per chat. Unknown harnesses can use manual inbox checks.

A PA is optional. Direct scoped messages need no management relay or elected management chat. `chat` commits a correlated request, then a configured native adapter can nudge the exact target; it does not replace that target with a new task worker. New workers are a separate explicit operation.

Choose worker history at setup: result-only/no-persist where verified, or supported native retention/cleanup. Archive/delete currently applies only to persisted Codex workers. An acknowledged successful durable result and verified exit are required before cleanup; failures/uncertainty preserve evidence. N-hour cleanup can wait until next startup, with no hidden scheduler or zero-residue promise.

Skills and project memory remain in user-chosen canonical locations; native adapters reference them separately. Installation does not replicate sessions or transfer ownership. Handover requires source stop and destination acceptance.

Candidate implementation checks and remaining native behavior gaps are listed in [validation](validation.md). Native configuration loading, live delivery, process cleanup and end-to-end cutover are separate outcomes.
